## 1. Docker and containers

**Versions.** Docker Desktop **4.84.0 (2026-07-27)**, on a weekly cadence (4.83.0 on 2026-07-20) ([docs.docker.com/desktop/release-notes](https://docs.docker.com/desktop/release-notes/)). Docker Engine **29.6.2 (2026-07-16)** ([docs.docker.com/engine/release-notes/29](https://docs.docker.com/engine/release-notes/29/)).

**Engine 29 is the real breaking change of this cycle.** On fresh installs the **containerd image store is now the default** (excluding `userns-remap` daemons); upgraded daemons keep overlay2 until you opt in. Minimum API version jumps to **v1.44** (Docker 25.0+), so old clients break. **Docker Content Trust was removed from the CLI** — signing is now cosign/sigstore territory. `nftables` arrives as an experimental `firewall-backend`, the first credible exit from Docker's iptables rule-mangling. cgroup v1 is deprecated but supported through **May 2029** ([same source](https://docs.docker.com/engine/release-notes/29/)).

**Licence — the commercial trigger.** Docker Desktop requires a paid subscription unless the company has **fewer than 250 employees AND less than $10M annual revenue**; government entities are never eligible for free use ([docker.com/pricing/faq](https://www.docker.com/pricing/faq/)). Pro $9, Team $15, Business $24 per user/month annually ($11/$16/$24 monthly) ([docker.com/pricing](https://www.docker.com/pricing/)). This is a headcount question, not a usage question — at MNC scale, every developer laptop running Docker Desktop is a licensed seat.

**Build Cloud / Bake / Scout entitlements** (all from [docker.com/pricing/faq](https://www.docker.com/pricing/faq/)): included Build Cloud minutes are Personal 100 (trial), Pro 200, Team 500, Business 1,500 per month, with **no on-demand overage** — extra minutes are pre-purchased in 500–20,000 blocks and expire at term end. Scout-enabled repos: Personal 1, Pro 2, Team/Business unlimited. `docker buildx bake` is the free declarative front-end (HCL/JSON/Compose) that local BuildKit and Build Cloud consume unchanged — the right way to express multi-target, multi-platform builds.

**AI features.** Docker Model Runner supports **llama.cpp** (GGUF), **vLLM** (Safetensors, Linux x86_64 / WSL2 + NVIDIA) and **Diffusers**, exposes **OpenAI- and Ollama-compatible APIs**, and pulls models from Docker Hub, OCI registries or Hugging Face ([docs.docker.com/ai/model-runner](https://docs.docker.com/ai/model-runner/)). The docs state no GA/beta status — maturity **UNVERIFIED**.

**Hub rate limits.** Unauthenticated **100 pulls / 6 hours per IPv4 or IPv6 /64**; Personal **200 / 6 hours**; Pro/Team/Business unlimited ([docs.docker.com/docker-hub/usage/pulls](https://docs.docker.com/docker-hub/usage/pulls/)). The /64 clause is what kills shared CI runners and NAT'd offices. The fix is a **pull-through cache** (registry mirror, Harbor, ECR/Artifactory remote repos) plus authenticated CI pulls — not a bigger plan.

**Where the alternatives win.** Podman **v6.0.2 (2026-07-22)** is the default on RHEL-family servers: daemonless, rootless-first, systemd-native (Quadlet), no Desktop licence. containerd 2.3.3 + nerdctl 2.3.5 when the host is already a Kubernetes node. Buildah 1.44.0 for scriptable builds with no Dockerfile. On macOS, **Colima** (MIT) and **Rancher Desktop** (Apache-2.0) carry no seat cost; **OrbStack** is fastest but free only for personal/non-commercial use, $8/user/month commercially — a licence swap, not a licence escape. **Now confirmed against the vendor page, not blogs:** orbstack.dev/pricing lists Free as "Personal, non-commercial use", **Pro at $8/user/month ($96 billed annually)** with "Commercial use" as the named Pro entitlement, and Enterprise at custom pricing ([orbstack.dev/pricing](https://orbstack.dev/pricing)).

**CI builders: one correction.** **Kaniko is archived** — `archived: true`, last push **2025-06-03** (GitHub API). Any 2026 blog recommending it is stale. Use BuildKit standalone (`buildkitd`/`buildctl`), Buildah, or Buildpacks (`pack` v0.40.8).

**Image hygiene.** Multi-stage builds plus a minimal runtime base is table stakes; Distroless and Wolfi/Chainguard are the two credible minimal-base families. **Docker Hardened Images** — **corrected: both halves of what I wrote here were wrong.** The free tier is not a cut-down "OSS catalog": Docker's own press release of **2025-12-17** open-sourced the **full catalog of 1,000+ DHI under Apache 2.0**, stating it "allows everyone: developers, maintainers, hobbyists, teams, governments, and organizations to use, share, and build on DHI with clear rights and no hidden restrictions" ([docker.com press release](https://www.docker.com/press-release/docker-makes-hardened-images-free-open-and-transparent-for-everyone/)). So the "Apache-2.0, no restrictions" framing is the **vendor's own**, not a blog embellishment — my UNVERIFIED flag was misplaced. Nor is commercial pricing unpublished: the tiers are **Community (free), Select, Enterprise and ELS**, with **Select listed from $5,000 per repo/year** ([hub.docker.com/hardened-images/plans](https://hub.docker.com/hardened-images/plans), [docs.docker.com/dhi](https://docs.docker.com/dhi/)); only Enterprise and ELS are contact-sales. `cosign` v3.1.2 (Apache-2.0) for SBOM/signing matters more now that Content Trust is gone.

**Repos to study** (API-verified): `moby/moby`, `moby/buildkit`, `podman-container-tools/podman`, `containerd/nerdctl`, `sigstore/cosign` — all **Apache-2.0**, all active. ## 2. Linux

**The kernel is on 7.x.** Mainline **7.2-rc5 (2026-07-26)**, stable **7.1.5 (2026-07-24)**, longterm **6.18.40, 6.12.98, 6.6.145, 6.1.178, 5.15.212, 5.10.261** ([kernel.org](https://www.kernel.org/)). The 6→7 jump was cosmetic: Torvalds bumps the major after x.19, not for any single feature ([theregister.com](https://www.theregister.com/2026/02/09/linux_6_19_7_named/)). **6.18 is the LTS line** you will meet in enterprise distros — now confirmed against a primary kernel.org page rather than Phoronix: [kernel.org/category/releases.html](https://www.kernel.org/category/releases.html) lists 6.18 as **longterm, maintained by Greg Kroah-Hartman & Sasha Levin, projected EOL Dec 2028** (the page cautions that projected EOLs "are not set in stone" and usually start at two years). Substantively: slab "sheaves" per-CPU caching, XFS online fsck on by default, `dm-pcache`, TCP AccECN.

**Correction on the Rust framing.** I wrote that Rust was "promoted to a supported in-tree language" at 7.0. That does not hold up: `CONFIG_RUST` in `init/Kconfig` reads plainly `bool "Rust support"` — with no `EXPERIMENTAL` marker — at **v6.12, v6.15, v6.16, v6.17, v6.18, v6.19, v7.0 and v7.1** alike, so 7.0 is not the promotion point (checked against the tagged trees at raw.githubusercontent.com/torvalds/linux). The cited 9to5linux article now returns HTTP 403 and no kernel.org or `Documentation/rust/` page makes the claim. Rust's in-tree status and the "first fully-Rust drivers landing around 7.0" timing are therefore **UNVERIFIED** — do not repeat either as a 7.0 headline feature. The per-release attribution of the four features above is likewise sourced only to release-summary journalism and is **UNVERIFIED** at the granularity of "which of 6.18/6.19/7.0 shipped what".

**Enterprise distros.** RHEL 10.2 and 9.8 shipped **2026-05-19** — *corrected from 2026-05-20*; Red Hat's own release-dates table gives GA **2026-05-19** for both (RHEL 10.2 = RHBA-2026:18131, kernel 6.12.0-211.7.1.el10_2; RHEL 9.8 = RHBA-2026:18586, kernel 5.14.0-687.5.1.el9_8) ([access.redhat.com/articles/red-hat-enterprise-linux-release-dates](https://access.redhat.com/articles/red-hat-enterprise-linux-release-dates)). 2026-05-20 is the publication date of the Red Hat *Developer* write-up, not the GA date. RHEL 10 requires **x86-64-v3**; AlmaLinux 10 deliberately kept an **x86-64-v2** build — confirmed by AlmaLinux directly: it ships v3-optimised binaries by default but adds "an additional x86-64-v2 architecture, allowing users on that older hardware to continue to receive security updates for another 10 years" ([almalinux.org](https://almalinux.org/blog/2025-05-27-welcoming-almalinux-10/)). One caveat that matters at MNC scale: AlmaLinux notes third-party RHEL 10 packages target v3, so the v2 build suits only default-package-set workloads or fleets willing to rebuild. This remains the single best reason to pick Alma over Rocky for older fleets. Rocky 10 added RISC-V (**UNVERIFIED** — sourced only to [openlogic.com](https://www.openlogic.com/blog/rhel-10-features-overview), a vendor blog, not a Rocky release note). Ubuntu LTS is **5 years standard → 10 with Pro ESM → 15 with the Legacy add-on**; 24.04 runs to May 2029 / 2034 / 2039, 26.04 to ~May 2041 ([ubuntu.com/about/release-cycle](https://ubuntu.com/about/release-cycle)). The oft-quoted "12 years" is Canonical's *floor*, not the ceiling.

**Immutable/atomic is where the interesting work is.** Talos v1.13.7 (MPL-2.0) — no shell, no SSH, API-only, Kubernetes-only. Flatcar (Apache-2.0) for A/B-updated container hosts. Fedora CoreOS + **bootc** (v1.16.6, dual MIT/Apache-2.0) for "the OS is an OCI image"; RHEL image mode is bootc productised, with `bootc upgrade --download-only`, soft reboot for seconds-long updates, and Tech Preview sealed images signed with your own keys ([developers.redhat.com](https://developers.redhat.com/articles/2026/11/17/image-mode-rhel-10-updates-seconds-soft-reboot)). AlmaLinux ships bootc images for x86_64 and aarch64 ([almalinux.org](https://almalinux.org/blog/2024-09-02-bootc-almalinux-heliumos/)).

**systemd keeps eating.** Current tags include **v261.2 (2026-07-23)**, with 259/260 still getting backports (GitHub API). v259 (2025-12-17) made journald **persistent by default**, dropped TPM 1.2, moved networking to **nftables**, added experimental **musl** support, extended **Varlink IPC considerably** — the NEWS wording is that it "has been extended considerably" and now exposes `Reload()` and `Reexecute()` "mirroring the calls of the same name accessible via D-Bus"; my original "D-Bus parity" overstated it — and **deprecated SysV init scripts with removal scheduled for v260** ([lwn.net](https://lwn.net/Articles/1051163/), [phoronix.com](https://www.phoronix.com/news/systemd-259)).

**The v260 removal landed — verified against the NEWS file, not inferred.** `CHANGES WITH 260` opens its "Feature Removals and Incompatible Changes" section with "Support for System V service scripts has been removed. Please make sure to update your software *now*…", and names the three components dropped: `systemd-rc-local-generator` and `rc-local.service`, `systemd-sysv-generator`, and `systemd-sysv-install`. The meson options `-Drc-local=`, `-Dsysvinit-path=` and `-Dsysvrcnd-path=` are deprecated pending a later drop. One escape hatch worth knowing: v260 **restored** the `runlevel[0-6].target` units removed in v258, enableable via the new `-Dcompat-sysv-interfaces=yes` meson option ([NEWS at tag v260](https://raw.githubusercontent.com/systemd/systemd/v260/NEWS)). So any RHEL/SLES-era estate still shipping `/etc/init.d` scripts breaks on a v260+ systemd, not merely warns.

**Wayland has effectively won.** **Corrected — I had the GNOME version and the verb wrong.** GNOME 49 did *not* remove the X11 session code; it **disabled it by default**. GNOME's own release notes say "Support for a dedicated X11 session has been disabled by default in GNOME 49" across `gnome-session`, `gdm`, `mutter` and `gnome-shell`, and that "X11 support can still be enabled as a build option for each of these modules, though distributions should be aware that this may not be possible in future GNOME versions" ([release.gnome.org/49/developers](https://release.gnome.org/49/developers/)). Removal was planned for **GNOME 50** — which is what **Ubuntu 26.04 actually ships** ("The GNOME desktop environment has been updated to version 50"), not GNOME 49. Ubuntu's 26.04 release notes confirm X11 code cleanup (PreLogin/PostSession scripts removed) but do **not** state that GNOME-on-X11 "cannot be installed at all", so that stronger claim is **UNVERIFIED** ([documentation.ubuntu.com/release-notes/26.04](https://documentation.ubuntu.com/release-notes/26.04/changes-since-previous-interim/)). KDE plans full X11 session removal in **Plasma 6.8** (~late 2026); XWayland remains the compatibility layer ([blogs.kde.org](https://blogs.kde.org/2025/11/26/going-all-in-on-a-wayland-future/), [linuxiac.com](https://linuxiac.com/kde-plasma-6-8-will-go-fully-wayland-ending-nearly-30-years-of-x11-sessions/)). XLibre is an Xorg fork most distros are not packaging — niche.

**Learn now vs legacy trivia.** Learn: **eBPF** (bpftrace, bcc, Cilium v1.19.6 — the most-used production CNI per CNCF), systemd units/timers/Quadlet/`systemd-analyze`, cgroup v2, namespaces and rootless UID mapping, nftables (not iptables), `bootc`/image-mode thinking, journald. Legacy trivia: SysV init scripts, `ifconfig`/`route`/`netstat`, raw iptables chains, X11 session tuning, `/etc/rc.local`.

**Repos to study:** `siderolabs/talos` MPL-2.0 · `systemd/systemd` GPL-2.0 · `cilium/cilium` Apache-2.0 · `bpftrace/bpftrace` Apache-2.0 · `bootc-dev/bootc` (API **NOASSERTION**; LICENSE states dual MIT **OR** Apache-2.0). Flags: `torvalds/linux` and `libbpf/libbpf` also return **NOASSERTION** — libbpf's LICENSE reads `LGPL-2.1 OR BSD-2-Clause`, Linux's `COPYING` is GPL-2.0 plus a syscall note — the SPDX field is unusable for automated compliance here. `rocky-linux/rocky-tools` last pushed **2025-07-16** (stale).

## 3. Kali Linux

**Cadence is quarterly on a rolling Debian base** (`kali-rolling`). **2026.1** (late March 2026): kernel 6.18, 8 new tools, BackTrack retro mode, 25 packages added / 9 removed / 183 updated ([kali.org](https://www.kali.org/blog/kali-linux-2026-1-release/), [helpnetsecurity.com](https://www.helpnetsecurity.com/2026/03/25/kali-linux-2026-1-release/)). **2026.2** (~end June 2026): kernel **6.19** — deliberately *not* 7.0, which breaks NVIDIA DKMS, an explicit stability-over-latest-security-patches trade-off with 7.0 parked in `kali-experimental`; GNOME 50 and Plasma 6.6; **initrd cut from 200 MB to 60 MB** with ~3× faster QEMU boots; nine new tools (`arsenal-ng`, `legba`, `oletools`, `shell-gpt`, `tailscale`, `tookie-osint`, `uro`, `Penelope`, re-added `hydra-gtk`); NetHunter qcacld-3.0 injection on more devices, NetHunter Pro +24 phones. **The kali.org 403 has cleared and the primary source now confirms the kernel decision in Kali's own words:** "we decided to release with a 6.19 kernel to avoid breaking NVidia users", after "reports of incompatibilities with the NVidia DKMS drivers", with "the kernel 7.0 ready for you in `kali-experimental`". The initrd and boot figures are also Kali's own (≈200 MB → 60 MB for VM images, achieved by removing graphics firmware; "boot time is cut by ~3x", caveated as system-dependent), and the nine tools match ([kali.org/blog/kali-linux-2026-2-release](https://www.kali.org/blog/kali-linux-2026-2-release/); secondary coverage: [bleepingcomputer.com](https://www.bleepingcomputer.com/news/linux/kali-linux-20262-released-with-9-new-tools-nethunter-updates/), [9to5linux.com](https://9to5linux.com/kali-linux-2026-2-released-with-gnome-50-kde-plasma-6-6-and-new-tools)). The NetHunter "+24 phones" count is not stated in those terms on the Kali post — **UNVERIFIED**.

**Metapackages** are the correct mental model: `kali-linux-core` → `kali-linux-headless` → `kali-linux-default` (desktop ISO set) → `kali-linux-large` (previous default) → `kali-linux-everything`, plus `kali-linux-arm`, `kali-linux-nethunter`, `kali-linux-labs`, eight `kali-desktop-*`, and topic packs `kali-tools-{information-gathering,web,passwords,wireless,exploitation,forensics,post-exploitation,rfid,sdr,voip,…}` ([kali.org/docs/general-use/metapackages](https://www.kali.org/docs/general-use/metapackages/)). On a server or CI box, install the specific `kali-tools-*` on Debian rather than deploying Kali.

**Kali Purple** is a metapackage selection for defensive work mapped to NIST CSF 2.0 functions — `kali-tools-identify / -protect / -detect / -respond / -recover` — marketed as "SOC-in-a-box" with 100+ tools, refreshed artwork in 2026.1 ([stationx.net](https://www.stationx.net/kali-purple-guide/)). Useful as a lab bundle; treat "replaces your SIEM" claims as **UNVERIFIED marketing**.

**When Kali is the wrong choice — from Kali's own docs.** Kali is "specifically geared towards professional penetration testers and security specialists" and is "NOT a recommended distribution if you're unfamiliar with Linux." Network services are disabled by default via systemd hooks and blocklists, the kernel is patched for wireless injection, and the docs explicitly warn against adding PPAs or third-party repos ([kali.org/docs](https://www.kali.org/docs/introduction/should-i-use-kali-linux/)). So: **never** a daily driver, server, container base image, or build agent. Use Debian/Ubuntu for those; keep Kali as a disposable audit VM, WSL2 instance (`kali-win-kex`), ARM/Raspberry Pi field device, or cloud image torn down after the engagement.

**Alternatives.** Parrot OS Security is also Debian-based but ships hardened defaults and a Home edition intended for daily use — the better pick for one machine doing both work and audit. BlackArch is an Arch *overlay*: you add tool packages to an existing Arch install rather than installing a distro, which suits Arch users and nobody else (tool counts **UNVERIFIED**).

The real caveat is narrower than I implied and should be stated precisely: the file adds "This license does not apply to third-party components", so the framework core is BSD-3-Clause and the bundled modules/dependencies are what need diligence before redistributing.) **Flag: `nmap/nmap` is NOASSERTION and its LICENSE is the Nmap Public Source License v0.95 — a custom, non-OSI licence with a contributor agreement and redistribution restrictions. ## 4. Ansible and config management

## 5. Java

**LTS state.** Java **25 is the current LTS** (Sept 2025). **Java 21's permissive licensing ends September 2026** — updates after that move to the Java SE OTN licence, the same paid-support licence as 8/11/17. Oracle JDK 17 already moved to OTN on **2024-10-15**. Oracle's own words: users wanting permissively-licensed Java after September 2026 "should upgrade to Oracle JDK 25 or later." **The next LTS is Java 29 in September 2027** — not 27 ([Oracle Java SE Support Roadmap, updated 2026-04-02](https://www.oracle.com/java/technologies/java-se-support-roadmap.html)). **This is the NFTC trap and it fires in two months.** If you are on Oracle JDK 21 binaries, you are about to be out of free updates; switch vendor or move to 25.

**Release train.** JDK 26 GA **2026-03-17**, 10 JEPs, removing the Applet API and adding AOT object caching (JEP 516) and HTTP/3 in the HTTP client ([oracle.com/news](https://www.oracle.com/news/announcement/oracle-releases-java-26-2026-03-17/), [infoworld.com](https://www.infoworld.com/article/4050993/jdk-26-the-new-features-in-java-26.html)). JDK 27 is in **Rampdown Phase Two**, feature set frozen, **GA 2026-09-15**, with 9 JEPs: **523** G1 as default GC everywhere, **527** post-quantum hybrid key exchange for TLS 1.3, **531** Lazy Constants (3rd preview), **532** Primitive Types in Patterns (5th preview), **533** Structured Concurrency (**7th preview**), **534** Compact Object Headers **by default**, **536** JFR in-process data redaction, **537** Vector API (12th incubator), **538** PEM Encodings (3rd preview) ([openjdk.org/projects/jdk/27](https://openjdk.org/projects/jdk/27/)).

**Read the preview counts as a warning.** Virtual threads, records, sealed types, pattern-matching switch and the Foreign Function & Memory API are *final* and safe to build on. **Structured concurrency is still preview at its seventh iteration, Vector API at its twelfth incubation** — neither belongs on a critical path without `--enable-preview` discipline and an upgrade plan. **Project Leyden** lands incrementally (AOT class loading → method profiling → object caching), and **CRaC** (`openjdk/crac`, GPL-2.0) is the checkpoint/restore route to millisecond starts — the pragmatic alternative to native-image for Spring.

**GraalVM.** Oracle GraalVM ships under **GFTC**, permitting free commercial and production use including Native Image output; Community Edition is **GPLv2 with Classpath Exception** ([graalvm.org/faq](https://www.graalvm.org/faq/)). Current CE build **graal-25.2.4 (2026-07-28)** (GitHub API). Native Image is production-real for Quarkus/Micronaut and serverless; for large Spring apps, CRaC or Leyden AOT usually beats fighting reflection metadata.

**Frameworks.** **Spring Boot 4.1.0 (2026-06-10)**; 4.0.0 shipped 2025-11-20 on **Spring Framework 7** — **Java 17 minimum**, first-class Java 25, full modularization into smaller jars, JSpecify null-safety, API versioning, declarative HTTP service clients ([spring.io](https://spring.io/blog/2025/11/20/spring-boot-4-0-0-available-now/)). Boot 4 is a genuine major migration; budget for it. **Quarkus 3.37.4** for Kubernetes-native, native-image-first services. **Micronaut 5.1.10** for compile-time DI with no reflection, where cold start and memory ceiling dominate. **Helidon 4.5.1** runs blocking code on virtual threads — least ceremony if you already think in plain Java and Loom.

**Build tooling.** Gradle **9.6.1 (2026-06-26)** (9.7.0-RC1 in flight) — configuration cache and Kotlin DSL make it the default for complex multi-module or Android work. **Maven 4 is still not GA: newest tag is `maven-4.0.0-rc-6` (2026-07-28)**, with 3.9.16 (2026-05-17) the shipping stable line (GitHub API). **GA status now re-checked at Apache itself, not just GitHub, and it holds:** [maven.apache.org/download.cgi](https://maven.apache.org/download.cgi) offers **3.9.16 as the only GA release** ("recommended for all users") and lists Maven 4.0.0 solely as a release candidate that is "**NOT** safe for production use". Two wrinkles worth noting: the Apache download page still advertises **rc-5** while GitHub has already tagged rc-6, so the two disagree on the current RC; and a **`maven-3.10.0-rc-1`** (2026-07-13) now exists on the 3.x line, which the original text did not mention. Enterprise/banking remains overwhelmingly Maven — defensible, since declarative POMs audit in a way Gradle scripts do not.

**JDK distribution choice.** Pick a build, not a brand: **Temurin** as neutral default — **but the repo attribution here was wrong.** `jdk-25.0.4-ga` (2026-07-22) is a release of **`adoptium/temurin25-binaries`**, and that repo returns **`license: null`** in the API. `adoptium/temurin-build` *is* Apache-2.0, but it is the build *tooling* repo and its newest release is **`v2023.01.03` (2023-01-13)** — over three years stale, and it carries no JDK version tags at all (`git/matching-refs/tags/jdk-25.0.4` returns empty). Cite the binaries repo for versions and the build repo for the Apache-2.0 licence; do not merge them, and do not read `temurin-build`'s dormancy as Temurin being unmaintained. **Corretto** (GPL-2.0) if AWS-centric; Liberica for JavaFX/embedded/ARM; Zulu for long paid tails. Avoid Oracle JDK binaries unless you hold a Java SE subscription or are firmly on 25+. New Relic's *State of the Java Ecosystem* is the usual vendor-share citation but the current edition 404s at its primary URL — the quoted "Oracle 21%, Amazon 18%, Adoptium 18%" split is from the **2024** report ([newrelic.com PDF](https://newrelic.com/sites/default/files/2024-05/new-relic-state-of-the-java-ecosystem-2024-05-29.pdf)); any 2026 figure is **UNVERIFIED**.

**Why Java still dominates enterprise/banking, and what to learn.** Multi-decade backward compatibility, the best-instrumented GC and profiling story in the industry (JFR, async-profiler), a stable LTS contract with multiple free vendors, and regulator-friendly auditability. To be employable: Java 21/25 language level (records, sealed interfaces, pattern-matching switch, virtual threads), Spring Boot 3.x→4.x migration mechanics, Maven, Testcontainers + JUnit 5, JFR diagnosis, and one of Quarkus/Micronaut. Learn the **licence map** too — knowing the September 2026 Oracle JDK 21 cliff is disproportionately valuable right now.
